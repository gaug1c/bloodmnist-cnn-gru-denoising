Research task — two new layers (10 minutes within the CNN section)¶

Before using these supplied layers, consult the official PyTorch documentation for BatchNorm2d and Dropout.

  1. In your own words, what does each layer do? Why might it help a classifier?

BatchNorm2d normalises the activations of each channel (zero mean, unit variance) This stabilises and speeds up training, reduces internal covariate shift, and allows higher learning rates.

Dropout randomly zeroes a fraction of activations during training, preventing the network from relying too heavily on specific neurons. This reduces overfitting by discouraging co-adaptation between units.

  1. How does each layer behave in model.train() and model.eval() modes?

BatchNorm2d: in train mode, it computes mean and variance from the current batch and updates its running statistics. In eval mode, it uses the accumulated running mean/variance instead, ignoring the current batch.

Dropout: active only in train mode, randomly zeroing units. In eval mode it is fully disabled — all units are used normally.

  1. What does p=0.25 mean for Dropout? What happens to the retained activations?

Each unit has a 25% probability of being zeroed at each forward pass during training. The remaining active units are scaled by 1/(1-0.25) = 1.33 to keep the expected activation sum roughly constant, so no adjustment is needed at evaluation time.

  1. Which values are learned by BatchNorm? What are its running statistics? Does Dropout have trainable parameters?

BatchNorm2d learns two trainable parameters per channel (γ and β), updated via backpropagation. Its running mean and variance are buffers, not parameters — they are updated by a moving average, not by gradient descent. Dropout has no trainable parameters — it is a fixed stochastic operation.

  1. Explain why evaluation must call model.eval() even inside torch.no_grad().

torch.no_grad() only disables gradient tracking to save memory/computation — it does not change layer behaviour. model.eval() is what actually switches BatchNorm2d and Dropout to inference mode. Without it, even with no gradients computed, results would still be inconsistent due to batch-dependent normalisation and active random dropout.

Convolution: Cout(Cin k²+1). Linear: dout(din+1). Batch normalisation: 2C (scale and shift). Explain why dropout, ReLU and pooling add no learned parameters.

ReLU, MaxPool2d and Dropout are fixed, parameter-free operations defined by a mathematical rule rather than learned weights. ReLU simply replaces negative values with zero (max(0, x)). MaxPool2d selects the maximum value within each local window. Dropout randomly zeroes activations according to a fixed probability p. None of these operations involve a weight matrix or bias vector that could be updated by backpropagation — they only filter, select, or reshape the values already produced by the preceding (parameterised) layer.

Q2¶

Why should CrossEntropyLoss receive logits rather than softmax probabilities? What is uniform-random accuracy for 8 classes? What do train(), eval() and no_grad() do?

PyTorch's CrossEntropyLoss internally combines LogSoftmax and negative log-likelihood loss in a single, numerically stable operation. If softmax probabilities were passed in instead of raw logits, the loss would effectively apply softmax twice, distorting both the loss value and the gradients. Computing log-softmax directly from logits also avoids numerical issues (overflow/underflow) that can arise from computing softmax and its logarithm as two separate steps.

With 8 balanced classes, guessing uniformly at random gives an expected accuracy of 1/8 = 12.5%. Any trained model should clearly exceed this baseline.

model.train() switches the model into training mode: BatchNorm2d uses current batch statistics and updates its running averages, and Dropout randomly zeroes units. model.eval() switches the model into evaluation mode: BatchNorm2d uses its accumulated running statistics instead of batch statistics, and Dropout is disabled. torch.no_grad() is a separate context manager that disables gradient computation and tracking, reducing memory and compute usage during inference. It does not affect the behaviour of BatchNorm2d or Dropout — it is typically used together with model.eval(), not as a replacement for it.

def fit_classifier(model, train_loader, val_loader, optimizer, criterion, epochs):
    history = {'train': [], 'val': []}
    best_loss, best_weights = float('inf'), None
    for epoch in range(epochs):
        model.train(); total, count = 0., 0
        for images, labels in train_loader:
            images, labels = images.to(device), labels.to(device)
            total += update_batch(model, images, labels, optimizer, criterion)*len(images)
            count += len(images)
        model.eval(); val_total = 0.
        with torch.no_grad():
            for images, labels in val_loader:
                val_total += criterion(model(images.to(device)), labels.to(device)).item()*len(images)
        val_loss = val_total/len(val_loader.dataset)
        history['train'].append(total/count); history['val'].append(val_loss)
        if val_loss < best_loss:
            best_loss = val_loss; best_weights = copy.deepcopy(model.state_dict())
        print(f'Epoch {epoch+1}: train={total/count:.4f}, val={val_loss:.4f}')
    model.load_state_dict(best_weights)
    return history

Q4 — What is the sequence?¶

Explain why one row is one time step and why there are 84 input features (28 pixels × 3 colour channels). Which tensor is the training target? Why are test noise and validation noise fixed?

My answers:

Each row of the image becomes one time step because the GRU processes a sequence element by element, similarly to reading a text word by word — here, "reading" the image row by row from top to bottom. Each row contains 28 pixels, and each pixel has 3 colour values (R, G, B), giving 28×3 = 84 input features per time step. A full image (28 rows) therefore becomes a sequence of 28 time steps, each with an 84-dimensional feature vector.

The training target is the clean image tensor, not the noisy one: the GRU receives the noisy image as input and is trained to reconstruct the corresponding clean image, which is the core idea of supervised denoising.

Validation and test noise are kept fixed (via a fixed random seed) so that evaluation is reproducible and comparable across epochs and across different model configurations. If the noise changed every time the model was evaluated, differences in validation/test loss could reflect a lucky or unlucky noise draw rather than a genuine improvement in the model's denoising ability.

        super().__init__()

Q5 — Architecture¶

Explain the RGB permutation and reshape. Why must the batch dimension be preserved? Why is the last hidden state insufficient here? Why sigmoid? Can the first reconstructed row use information from the last input row? Does a recurrent denoiser have to be an encoder–decoder?

My answer:

The RGB permutation and reshape: PyTorch stores images as (B, C, H, W), with channels before spatial dimensions. To treat the image as a sequence of rows, each time step must combine one row's pixel values together with their 3 colour channels. We permute to (B, H, W, C) so that H (the rows) becomes the sequential dimension, then merge W×C (28×3=84) into a single feature dimension, giving (B, 28, 84). At the output, the exact inverse operation reconstructs a valid image tensor.

Why the batch dimension must be preserved: Each image in the batch is independent of the others, so the batch dimension B must never be merged or reshaped along with the other dimensions — doing so would mix pixels from different images. Only the channel, height and width dimensions are reorganised; B is left untouched throughout.

Why the last hidden state alone is insufficient: The final hidden state only holds a single, compressed summary of the whole sequence (one 128-dimensional vector), which cannot by itself provide 28 separate row reconstructions of 84 values each. The model needs a different output at every time step, so it uses outputs (the hidden state at every step), not just the final hidden state.

Why sigmoid: Target pixel values are normalised to [0,1]. Sigmoid naturally outputs values in this range, ensuring the model's predictions stay within valid pixel bounds without requiring manual clipping afterward.

Can the first reconstructed row use information from the last input row? No. The GRU is unidirectional: when processing row 1, it has not yet seen rows 2 through 28 — it only has access to its initial hidden state (typically zero) and row 1 itself. It therefore cannot use any information from later rows. This is a structural limitation of a unidirectional GRU, unlike a bidirectional GRU which would have access to the full sequence context in both directions.

Does a recurrent denoiser have to be an encoder–decoder? No. This architecture is a simple many-to-many GRU that produces one output per time step directly, without a separate encoding phase that compresses the whole sequence before decoding it. An encoder–decoder scheme is needed when the output sequence has a different length than the input, or when a global summary must be formed before generation (e.g. machine translation). Here, each output row only depends on the past context (previous rows), so a straightforward many-to-many GRU is sufficient.

Q6 — Interpret the results¶

  1. Does restoration beat the “do nothing” baseline?

Yes, clearly: mean MSE drops from 0.0308 (noisy) to 0.0045 (restored), an 85.3% relative reduction, while mean PSNR improves from 15.1 dB to 23.5 dB (+8.4 dB) — a substantial and consistent improvement in reconstruction quality.

  1. Does the output preserve edges, textures and fine details? Discuss smoothing.

Not perfectly. Like most MSE-trained regression denoisers, the GRU tends to produce a somewhat smoothed reconstruction: MSE heavily penalises large localised errors, so the model learns to average plausible values rather than risk sharp but occasionally wrong predictions. Noise is largely removed, but fine cellular texture and sharp edges can appear slightly blurred compared to the original clean image.

  1. Does lower average MSE mean every image improves?

No. The reported MSE is averaged over 800 test images; individual images can have a higher MSE after restoration than before, as long as enough other images improve sufficiently for the overall average to decrease.

  1. Why is mean per-image PSNR different from PSNR computed using mean MSE?

PSNR involves a logarithm, a non-linear (concave) function. By Jensen's inequality, the mean of the logs is generally not equal to the log of the mean: mean(log(1/mse_i)) ≠ log(1/mean(mse_i)). Images with a poor (high) individual MSE produce a disproportionately low individual PSNR, pulling the per-image average PSNR down differently than a single PSNR computed from the overall mean MSE would be affected.

  1. What limits this GRU's access to spatial context?

Two structural factors: (1) unidirectionality — at row n, the model only has access to rows 1 through n, never to later rows, so it lacks any "future" spatial context; (2) the model processes the image as a 1D sequence of rows, so vertical relationships between distant rows are only accessible indirectly through the compressed hidden state, unlike a CNN which directly captures local 2D neighbourhoods via its convolutional kernels.

6. Optional experiment — choose ONE¶

  • Hidden size 32: calculate parameters, train, compare on validation.
  • Stronger noise: keep weights fixed and evaluate robustness, without selecting a new model on test.
  • CNN accuracy on clean/noisy/restored classification-test images. Use the common held-out test images and keep both models fixed. Does lower MSE imply higher accuracy?

I chose to compare hidden size 32 against the original hidden size 128. Reducing h from 128 to 32 cuts the GRU-alone parameter count from 82,176 to 11,328, and the total model from 93,012 to 14,100 parameters — a 6.6× reduction.

Hypothesis: a smaller hidden state has less capacity to encode row-to-row context, so I expected validation MSE to increase (worse restoration) compared to h=128, though not catastrophically, since per-row denoising may not require very high-dimensional context.

Result: on the validation set, h=128 achieves MSE=0.00458 (PSNR=23.51 dB), while h=32 achieves MSE=0.00744 (PSNR=21.43 dB) — a 62.6% relative increase in MSE and a 2.08 dB drop in PSNR. This confirms the hypothesis: reducing capacity by 6.6× does degrade restoration quality, but only moderately — the smaller model still performs far better than doing nothing (noisy baseline MSE=0.0308), suggesting a reasonable capacity/performance trade-off is available if a lighter, faster model were needed in practice.

7. Conclusion and submission (10 min)¶

Write 5–10 lines comparing the CNN's classification task and the GRU's reconstruction task. Explain their outputs, losses, parameter sharing and observed limitations.

Conclusion:

The CNN and GRU tackle fundamentally different tasks with different underlying principles. The CNN performs discrete classification, outputting 8 logits per image and reaching 90.9% test accuracy, relying on spatial parameter sharing: the same convolutional filters slide across the entire image, detecting local patterns (edges, textures) regardless of their position. The GRU instead performs continuous image reconstruction, producing 84 pixel values at every time step, relying on temporal parameter sharing: the same recurrent weights are reused at every row of the image, substantially reducing noise (85.3% relative MSE reduction, +8.4 dB PSNR gain over the noisy baseline).

Both models show characteristic limitations. The CNN confuses visually similar classes, most notably immature granulocytes with monocytes, reflecting genuine biological similarity between these cell types. The GRU tends to smooth fine details, a consequence of its MSE-based training objective and its strictly unidirectional access to spatial context — it can never use information from rows that come later in the sequence. The optional hidden-size experiment (h=32 vs h=128) confirmed that reducing capacity by 6.6× (93,012 → 14,100 parameters) moderately degrades restoration quality (MSE +62.6%, PSNR −2.08 dB) without collapsing it, showing that a meaningful capacity/performance trade-off exists for this task.
